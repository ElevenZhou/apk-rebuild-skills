# 任意作品逆向重建 — 标准工作流 SOP

> 版本：**v1.4.1（2026-11-09）**，与 `skills/rebuild-workflow/SKILL.md` 对齐（八阶段 S0–S7）
> 用途：任何"只有 APK/EXE、无源码、需重建可迭代新项目"的任务，照此流程执行，不依赖执行者个人经验。
> 配套：[docs/ARCHITECTURE.md](ARCHITECTURE.md)（v1.4.0 架构图：分层、流程、人机边界）、`自家APK逆向重建-技术方案.md`（工具选型与调研底稿）、`skills/rebuild-workflow/references/prior-art.md`（现成成果检索）
> 演进规则：每个项目结束后，把新踩的坑、新经验回写本文档与对应 skill，版本号 +0.1；**改完按 `retro-checklist.md` 同步到 GitHub / Y 盘 / 各 Agent 安装点**。

## 〇、合规模型（v1.4.0 起）

**分析放行 / 发布管控**：允许**所有作品**（公司自有、权属待确认、第三方、来源未知）进入分析与重建流程；S0 只登记权属状态，不阻断开工。**正式发布前必须逐产品人工确认所有权，并由人工执行发布**（G-PUBLISH）；未确认则只能出 `仅内部` 的试玩包与工程。判断口诀：**能不能分析 ≠ 能不能发布**。

分析范围仍逐项勾选（静态 / 真机动态 / 联网与服务端 / 产物用途），**没勾 = 不做**。全程安全红线：禁止绕过登录、风控、证书校验或服务端访问控制；不复用第三方生产服务；不公开发布反编译产物。

## 一、总流程（八个阶段，严格按序）

```
A0 原包获取（前置动作，不占阶段编号）→ S0 立项登记 → S1 侦察解包 → S2 静态分析 → S3 资源回导
→ S4 方案拍板 → S5 里程碑开发(M0-M5) → S6 真机采证校准
→ S7 打包交付
```

**A0 原包获取（流程第一步）**：**有包就进，没包才下**。已提供本地 APK/XAPK/EXE → 只做校验、归档、登记来源，直接进 S0；否则按用户给的**游戏名 / Google Play 详情页链接 / 三方市场下载链接**下载（脚本 `skills/rebuild-workflow/scripts/fetch_artifact.py`，细则 `artifact-acquisition.md`）。游戏名会搜出多个候选包名，**必须由负责人确认**，Agent 不得自选；Play 链接只用于取包名，包体来自公开镜像。A0 出口：文件头与大小校验、sha256 写入 scope.md、`input/artifact-source.json` 留痕、商店页链接记入输入 #6。付费 / 登录 / 区域受限应用由负责人提供包体，不绕过反爬、验证码或会员墙。

**P 横切检查点（不占阶段编号）**：`P0` 在 S0→S1 门口查现成成果与工具候选，`P4` 在 S2→S4 门口查同类玩法实现；见 `prior-art.md`。
**G-PUBLISH 发布人工门禁**：S7 之前，逐产品人工确认所有权、人工执行发布；未确认 → 仅内部。

**铁律（七条）：**
1. **先登记后动手**：scope.md 记录权属状态、范围边界与 P0 结论；只做已勾选的分析类型。权属未确认**不阻断分析与重建**，但阻断正式发布；
2. **先文档后编码**：docs/ 01-09 齐全并过人工复核，才允许写第一行重建代码；
3. **先骨架后血肉**：M0 工具链+空骨架跑通冒烟，才进 M1 功能；
4. **每阶段有出口标准**：达不到出口标准不进下一阶段（出口标准见各节）；
5. **不确定即登记**：所有"看不清/先跳过"当场进待优化清单，禁止口头记忆；
6. **禁止编造**：拿不准标 `P0 占位`，结论带置信度；外部旁证标 `external-reference`，不可升级为已验证；
7. **发布归人**：正式发布前逐产品人工确认所有权，发布由人执行；Agent 不得自动对外发布、上架或分发。

## 二、S0 立项登记（输入完整性要求）

### 必须拿到的输入

| 输入 | 形式 | 缺失后果 |
|---|---|---|
| APK/EXE 原包（**A0 产出**） | 文件 + **sha256 校验值** + 来源留痕 `input/artifact-source.json`；本地已提供直接进 S0，否则按游戏名 / Play 链接 / 三方链接下载 | 无法确权与基线锁定 |
| **权属状态登记** | 四选一：公司自有已确认 / 公司自有待确认 / 第三方 / 来源未知；附已知凭证（可为空） | **不阻断开工**；但 S7 正式发布前须逐产品人工确认（G-PUBLISH） |
| 范围边界 | **逐项勾选**：静态分析 / 真机动态 / 联网与服务端 / 产物用途。**没勾 = 未授权** | 分析越界 |
| 引擎类型 | 原生 Android / Unity Mono / Unity IL2CPP / Godot / 其他 | 决定 S2/S3 工具链 |

完整清单为必需 #1–#7 + 后续 #8–#10（S4 前补齐；C/S 型产品 #10 服务端信息为必需），见 `rebuild-workflow/references/input-checklist.md`。开工前先自查环境前置（ASCII 路径、JAVA_HOME 不含中文、显式 java、统一 sha256sum）。项目已有门禁与本 SOP 冲突时，**以更严格者为准**。

### 产出物

- `项目X/input/artifact-source.json`（A0 原包来源留痕）与下载/归档的原包
- `项目X/scope.md`（立项登记书：sha256、原包来源、权属状态、**`prior_art` P0 结论**、授权范围、**发布授权段**）
- `项目X/task_spec.yaml`（机读工单：artifact/authorization/goal/verification 四段）
- 目录骨架：`docs/ evidence/ extracted/ assets/ rebuild/ recon/ runs/`
- **P0 现成成果检索记录**（未命中也须留痕，见 `prior-art.md`）

## 三、S1 侦察解包

### 步骤

1. **哈希基线**：`sha256sum` 原包，写入 scope.md；
2. **类型识别**：`unzip -l` 看内容物（dex 数/lib 引擎 so/assets 特征）判定引擎与加固；
3. **解包**（XAPK/APKS 必须解开全部 `config.*.apk`、OBB、assetpack）：
   - 原生：`apktool d`（资源/manifest/smali）+ `jadx`（Java 伪代码）
   - Unity Mono：ApkTool + dnSpy 系
   - Godot：解 zip 取 .pck，GDRE Tools 回导
4. **产物登记**：`extracted/` 下分 apktool/jadx 两目录，写 `assets/manifest.json`（资源类型计数清单）。
5. **源码可恢复性结论**：逻辑层可读程度 / 资源可导出程度 / 加固 / 服务端依赖 → 给出 R1/R2/R3 建议，交 S1 决策门。

### 出口标准

- 引擎类型确认（machine-verified：解包日志）；
- 资源总量清单（类型×数量，含全部分包）；
- 是否加固/加密结论（加固则调整预期：文档靠动态补充）；
- 源码可恢复性结论。

## 四、S2 静态分析（文档基线）

### 产出：docs/01-09 固定九篇

| 篇 | 内容 | 置信度标注要求 |
|---|---|---|
| 01-概述 | 产品定位、版本线、公开商店数据 | 引用处标 human-reported/machine-verified |
| 02-功能模块 | 页面/场景/玩法逐一描述 | 录屏能对上的标 human-reviewed |
| 03-接口文档 | autoload/插件桥/埋点/AB 键/服务端点 | 照抄契约，标 machine-verified |
| 04-本地存储 | 存档结构、键名 | |
| 05-权限与SDK | 第三方 SDK 清单及用途 | |
| 06-异常与容错 | 断网/存档损坏/广告失败降级 | |
| 07-安全逻辑 | 加密/校验/cheat 面（重建时剔除） | |
| 08-资源清单 | manifest 详表（类型/数量/路径） | |
| 09-人工复核清单 | 所有不确定项汇总，供 S5 校准 | 每项标 P0-P2 |

### 方法要点

- **置信度三级制**贯穿所有文档：`machine-verified`（工具输出）/ `human-reviewed`（录屏比对过）/ `human-reported`（口述，待验证）；
- 拿不准的数值一律标 `P0 占位`（进 S6 真机校准），**禁止编造**；
- 涉及商业判断（原包在线、竞品关系）要联网核实商店页。

### 出口标准

- 09 篇齐全，09 里 P0 项全部登记进未来某里程碑；
- 项目负责人过目 docs/01 与 09（人工确认一次）。

## 五、S3 资源回导

### 管线（按引擎）

- Godot ctex→png、spine 回导、ogg 重封装（GDRE 或自写脚本）；
- Unity：AssetRipper/AssetStudio（注意 IL2CPP 用 roytu fork v39）；
- 原生：apktool res/ 直接可用。

### 规则

1. **样品先行**：每类资源先回导 3-5 个样品人工验收（M0 做的事），再批量；
2. **原始保留**：回导产物放 `rebuild/neosudoku/assets_imported/`，永不改动原件；
3. **验收记录**：样品验收表（尺寸/模式/能否正常 load）写进 M0-验收记录.md。

### 出口标准 = M0

- 工具链表（版本/位置/冒烟状态）；
- 新工程骨架（autoload 空实现、规则引擎可跑）headless 冒烟 0 错误；
- 资源样品 10/10 PASS。

## 六、S4 方案拍板（决策门 D1-D9）

方案文档迭代（v1→v2→v3），每个版本号对应一轮前提修订。决策门示例（项目 D 实际）：

| 门 | 决策 | 项目 D 结论 |
|---|---|---|
| D1 | 逆向深度 | 纯重做（源码确认丢失） |
| D2 | 差异化程度 | 骨架等价脸面不同（原包在架，禁像素级复刻） |
| D3 | 原位更新 or 新包名 | keystore 丢失 → 新包名 |
| D4 | 数值口径 | 占位+AB 调平 |
| D5 | 微创新点 | N1 连击/N2 图鉴/N3 闪电局 |

## 七、S5 里程碑开发（M0-M5）

### 里程碑模板（每个都按此结构）

```
M#-进展.md：
  交付清单（功能×实现×验证三列表）
  测试汇总（套件×断言数×结果）
  已知问题与待办（同步进待优化清单）
  下一步建议
```

### 里程碑划分（可复用的通用框架）

| 里程碑 | 内容 | 项目 D 对应 |
|---|---|---|
| M0 | 工具链+骨架+资源样品 | ✅ |
| M1 | 核心玩法闭环 | Star Battle 规则+对局+关卡 |
| M2 | 商业化 | 商店/订阅/广告模拟/埋点 |
| M3 | 留存系统 | 每日挑战/打卡/图鉴/个人资料/排行榜 |
| M4 | 真机校准 | 数值口径对原包逐项采证；**原包不可运行/联网时改为负责人数值审定 + 新包真机验收** |
| M5 | 换皮+发布 | 品牌/图标/导出包 |

### 开发过程纪律（防返工的核心）

1. **待优化清单是唯一登记处**：立即池/M3 池/M4 池/M5 池分组，每次开发节点过一遍立即池，能顺手做的清掉；完成移归档区（留日期）；
2. **测试先行于交接**：每个功能配 tests_dev/ 套件（headless 可跑），交付前全量回归；测试要防"跨日存档污染"（状态重置要彻底）；
3. **参数全部外置**：数值进 `cfg/*.yaml`（校准位），AB 键进 `cfg/ab_keys.json`；代码里只留兜底值+注释指向 cfg；
4. **降级方案思维**：依赖重的演出（如 Spine）先出降级版（静态贴图+Tween），登记升级路径，不阻塞主线；
5. **每个新功能过冒烟**：`godot --headless --quit-after 3` + grep `SCRIPT ERROR`；**注意还要 grep `nonexistent`**（运行时信号连接失败 headless 冒烟抓不到）。

## 八、S6 真机采证校准 / S7 打包交付与发布门禁

### 真机采证方法（项目 D 验证有效的闭环）

1. **ADB 全接管**（用户不用操作）：
   - `adb devices` 确认 → `monkey -p 包名` 启动 → `screencap` 截图；
   - **点击坐标必须像素定位**（PIL 找色块中心），禁止目测估算；
   - 截图喂视觉模型（Gemini）读状态：关卡/计数/生命/文案。
2. **用户自然游玩录屏**（复杂流程）：
   - 5 分钟录屏 → 1fps 帧差扫描找场景切变点 → 切变点±1.2s 抽帧 → 视觉模型批量读；
   - 比 ADB 硬点效率高，适合结算/广告/引导类一次性流程。
3. **采证结论立即落两层**：cfg（数值）+ 待优化清单（记录），文档 `M#-*.md` 存证。
4. **原包无法运行或联网**（如服务端已下线，项目 C）：S6 只做**新包验收**；数值在 S4 由负责人自定义/审定，P0 可"经负责人审定"关闭。

### 已验证的口径采证清单（通用）

- 开局预置数量/难度分档；
- 失误惩罚口径（扣多少、动效、是否留痕）；
- 输入交互精度（单击/双击窗口/长按各是什么语义，双击窗口 ms 级实测）；
- 结算文案策略（按玩家行为动态选择的，采"策略"而非"文案"）；
- 广告出现时机（哪些位置、无填充时表现）；
- 顶栏/HUD 信息架构（逐元素对齐）。

### S7 · G-PUBLISH 发布人工门禁（先于打包）

| 步骤 | 谁做 | 要求 |
|---|---|---|
| 区分包类型 | Agent | 内测/试玩包（仅内部）不过门禁；正式发布包必过 |
| 逐产品确认所有权 | **人工** | 书面凭证 + 确认人 + 日期，写进 `scope.md`「发布授权」段 |
| 合规复核 | **人工** | D2/D6 换皮完成、无第三方代码/素材违规引入、无第三方生产服务依赖 |
| 执行发布 | **人工** | 上架 / 外发 / 对外分发由人执行；Agent 只准备交付物 |
| 未确认 | Agent | 打 `仅内部` 标记，禁止对外分发，交付清单写明原因 |

**Agent 禁止**：自动上架、自动外发、代填所有权确认、把"scope.md 勾选拟对外发布"当作已授权。

### 打包发布（Android，项目 D 实战坑全录）

1. **前置**：导出模板（版本目录名=编辑器版本号）、build-tools（dl.google 仓库 XML 查真实文件名，新版本命名无次版本号如 `r36`）、JDK、keystore；
2. **全 ASCII 路径**：SDK/JDK/Godot/keystore/输出路径全放 C:/ 纯 ASCII 目录（中文路径导致 Godot 导出静默失败、OpenCV imwrite 返回 False）；
3. **keystore 三元组规则**：preset 里 debug/release 三元组（路径+user+password）要么全填要么全空，空串 ≠ 未填；
4. **终极坑——ETC2**：Windows 开发机默认 DXT，Android 导出要求项目设置 `rendering/textures/vram_compression/import_etc2_astc=true`；**缺它时导出校验失败但零错误文案**，唯一解法是读 Godot 源码找无文案的 valid=false 点；
5. 导出命令：`Godot_console --headless --path . --export-release "Android" out.apk`；
6. 安装：`adb install -r`；无证书报错=三元组没配。
7. **keystore 双人双地备份**：release keystore 与口令分别由两人保管、存两个物理位置（如 NAS + 离线介质），写交接记录；丢失 = 以后只能换包名（项目 D 的教训）。

## 九、Debug 方法速查（按症状）

| 症状 | 首查 | 项目 D 实例 |
|---|---|---|
| headless 冒烟过了但真机黑屏/功能失效 | grep stderr 的 `nonexistent`（信号连接失败类） | PanelContainer 无 pressed 信号 |
| Parse Error 指向奇怪行号 | 上一行的合并/转义错误（Python 改脚本的 \n 陷阱） | if 语句两行并一行 |
| 同类 API 换语言报不存在 | 该类型可能不支持 lambda/链式（PackedStringArray.map） | YAML 解析器 |
| 跨月/跨年后日期逻辑错 | 日期差算法（月×31 近似必错，用儒略日 ordinal） | streak 跨月断签 |
| Godot 导出失败但无错误文案 | 读 export_plugin 源码找无文案 valid=false | ETC2 |
| OpenCV imwrite 返回 False | 路径含中文 → imencode+tobytes 写 | 全项目通用 |
| ADB tap 无反应 | 目标坐标像素定位；双击窗口需 ~250ms 内 | 原包双击窗口 |
| 视觉模型读数不一致 | 用像素采样交叉验证（找色块/角点均值） | 区域矩阵反推失败教训：渐变色区域靠截图分类不可靠，用交互反馈验证 |
| 首验通过复验失败 | 测试间状态污染（存档持久化） | m3 跨日失败 |

## 十、文档与记忆体系（三层）

1. **项目层**（项目X/内）：scope/task_spec/方案v#/docs 01-09/M#-进展/待优化清单——**待优化清单是活文档，每天用**；
2. **工作区层**（通用工程/.workbuddy/memory/）：每日工作日志（YYYY-MM-DD.md，append-only）+ 长期记忆 MEMORY.md（30 天后日志蒸馏）；
